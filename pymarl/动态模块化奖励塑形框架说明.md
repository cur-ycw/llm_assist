# 动态模块化奖励塑形框架说明

可以把当前这套框架理解成一篇面向多智能体强化学习的"动态模块化奖励塑形框架"论文原型。下面按照"研究背景 -> 研究意义 -> 研究方法"的顺序，对框架进行系统说明。

---

# 一、研究背景

## 1.1 多智能体强化学习中的核心困难

当前任务是 SMAC 的 MMM2 场景，本质上属于典型的 cooperative multi-agent reinforcement learning。该类任务通常存在以下几个突出难点：

1. **环境奖励稀疏**
   - 智能体在大部分时间步都无法获得明确的正反馈。
   - 真正有价值的信号往往只出现在团战结果、单位生死、推进成败等较粗粒度事件上。
   - 这会导致训练早期探索成本高、学习效率低。

2. **信用分配困难**
   - 团队整体获得回报后，很难判断是哪一个局部行为真正带来了收益。
   - 例如在 MMM2 中，集火、拉扯、保护 medivac、阵型切换都可能影响最终胜负，但环境原始 reward 不会直接揭示这些结构信息。

3. **策略学习与行为结构之间存在断层**
   - QMIX 这类 value decomposition 方法可以学习协作，但其协作结构主要依赖环境回报反向塑造。
   - 当环境奖励过于粗糙时，模型容易学得慢，或者学到局部有效但长期不稳定的策略。

4. **手工 reward shaping 难以长期有效**
   - 传统做法通常通过手工设计若干 shaping reward 来引导行为，例如鼓励集火、鼓励移动或保护关键单位。
   - 但这些规则往往是静态的：
     - 适用于训练早期的 shaping 未必适用于训练中后期；
     - 某些模块起初可能有帮助，后期反而可能误导优化方向；
     - 一旦写入系统，通常缺乏在线修正机制。

因此，在多智能体场景中会出现一个典型矛盾：

- 单纯依赖原始奖励，训练信号太弱，探索效率不足；
- 单纯引入固定 shaping，又容易使辅助奖励压过环境主目标。

当前框架的核心动机，就是在这两者之间构建一个更强的中间层：**让奖励指导不仅存在，而且可以被选择、调节、替换和回滚，而不是一次性写死。**

## 1.2 为什么采用模块化奖励而不是单一 shaping

当前框架并没有把辅助奖励设计成单一的统一标量修正项，而是将其拆解为多个具有行为语义的 reward module，例如：

- 关注集火的模块；
- 关注保护 medivac 的模块；
- 关注攻击节奏与阶段转换的模块；
- 关注避免 idle 或低效行为的模块。

这样设计有三个直接原因：

### 第一，复杂协作行为天然由多个因素构成
MMM2 中的有效战术并不是由某一个单独原则决定的，而是多个局部偏好、局部行为约束与协作模式共同形成的。

### 第二，不同训练阶段需要的指导并不相同
训练初期更需要强先验来辅助探索，而中后期则更强调对环境真实目标的忠实优化。单一 shaping 很难同时适配这两个阶段。

### 第三，只有模块化之后，系统才能进行选择与替换
如果 shaping 是一个整体，只能调整它的强弱；但如果 shaping 是一个模块池，就可以进一步回答：

- 当前更应该依赖哪个模块；
- 哪个模块已经失效；
- 哪个模块应该被替换；
- 替换之后如果变差，是否能够回滚。

因此，模块化设计本质上是将 reward shaping 从"静态规则"推进为"可管理、可演化的结构"。

## 1.3 为什么引入 LLM

在当前框架中，LLM 并不是策略本体，也不直接控制智能体决策。它承担的是**模块生成器**的角色。

其职责主要包括：

- 初始化一组具有行为语义的 reward modules；
- 当某个模块被判定为低效或失灵时，生成 replacement proposal；
- 基于已有模块池的 family 与 coverage 信息，尽可能提出不同家族、不同覆盖面的候选模块。

也就是说，LLM 在这里提供的是**可描述、可修改的行为先验**，而不是替代 RL 主学习过程。最终策略优化主体仍然是 QMIX，LLM 只在奖励结构层面提供可编辑知识。这种分工比直接让 LLM 接管决策更稳定，也更适合做系统性实验。

# 二、研究意义

## 2.1 该工作的直接目标

这项工作的目标，不是设计一个比 QMIX 更大的端到端模型，而是解决一个更现实的问题：

**如何在不推翻现有 RL 主体的前提下，为多智能体训练加入一个可控、可迭代、可回滚的奖励指导层。**

这一目标的意义可以分为三个层次。

## 2.2 第一层意义：提高训练效率与稳定性

多智能体任务中最常见的矛盾是：

- 没有 shaping，训练慢、探索弱；
- shaping 太强，又会劫持原始任务目标。

当前框架试图同时处理这两个问题：

1. 通过模块化 shaping 提高早期学习效率；
2. 通过 beta 调控与 shaping 保护机制，避免辅助奖励压过环境奖励；
3. 通过生命周期管理替换失效模块，而不是长期保留无效指导。

因此，该框架并不是简单地"加 reward"，而是在构建一种**受控的辅助信号注入机制**。

## 2.3 第二层意义：将奖励设计从一次性工程变成在线迭代过程

传统 reward engineering 最大的问题在于，它通常是一次性离线完成的：

- 先设计奖励；
- 再固定下来训练；
- 若效果不好，再手工改写并重新实验。

当前框架往前推进了一步，它允许：

- 先生成一组初始模块；
- 在训练中观察每个模块的实际使用情况与贡献情况；
- 发现低信号模块；
- 生成候选替换模块；
- 通过 shadow / promote / rollback 链路验证替换是否有效。

这意味着 reward engineering 不再只是离线的经验工程，而是变成了一个**训练中的在线优化过程**。从研究角度看，这使得"奖励函数本身"也进入了可适应、可修正的学习闭环。

## 2.4 第三层意义：为可解释的奖励进化提供实验框架

与黑箱式端到端优化相比，当前框架有一个明显优势：**可追踪、可解释。**

系统中可以明确观察到：

- 每个模块的名称、语义与代码；
- 每个模块的 usage / contribution / activation；
- selector 的 entropy、switch rate 与 balance；
- 模块替换为何触发；
- 候选模块为何被拒绝、晋升或回滚。

因此，该框架不仅能够回答"是否提升了性能"，还能够回答：

- 提升来自哪一类行为指导；
- 哪类模块最容易失效；
- 替换通常在训练的哪个阶段发生；
- 生命周期机制是否真正开始工作。

这类结果比单纯报告最终胜率更具研究价值，因为它揭示了奖励结构在训练过程中如何演化。

# 三、研究方法

如果按照论文方法章节来组织，当前框架可以拆解为以下六个部分：

1. QMIX 主体学习器；
2. 模块化奖励池；
3. 动态 selector；
4. 受控辅助奖励注入机制；
5. 模块生命周期管理；
6. LLM 生成与替换机制。

## 3.1 总体框架概述

当前框架的主学习器仍然是 **QMIX**。也就是说，真正负责多智能体联合策略价值分解的主干并没有被替换。

在 QMIX 外部，系统额外引入了一层 **Dynamic Reward Agent**，其由以下组件构成：

1. **模块池（module pool）**
2. **模块选择器（selector）**
3. **辅助奖励注入机制**
4. **模块生命周期管理机制**
5. **LLM 模块生成与替换机制**
6. **训练监控与触发机制**

整个闭环可以表示为：

**环境状态 / transition -> reward modules 产生辅助信号 -> selector 决定如何路由与组合 -> learner 将辅助奖励注入 TD 学习 -> pool 根据训练反馈决定是否替换模块 -> LLM 提供候选新模块**

因此，该系统并不是在改变策略网络本身，而是在主学习过程外部构建了一层"奖励控制闭环"。

## 3.2 模块化奖励表示

### 3.2.1 基本思想

每个 reward module 都可以被理解为一个局部行为评分器。它读取当前 transition 中的状态、动作、单位关系等信息，并输出某种辅助 reward contribution。

例如，不同模块可能偏向于：

- 鼓励更合理的集火；
- 奖励战斗阶段切换时的行为转换；
- 惩罚无效攻击窗口或闲置行为；
- 鼓励对关键友军的保护。

多个模块共同组成 reward pool。

### 3.2.2 为什么使用模块池而不是单一模块

模块池设计带来两个重要效果：

1. **表达能力更细**
   - 不同行为先验由不同模块承担；
   - 单一错误模块不会破坏全部 shaping 语义。

2. **可替换性更强**
   - 当某个模块失效时，只需要替换局部模块，而不必重写整个 shaping 结构。

因此，模块池是后续 selector 与在线替换机制成立的前提。

## 3.3 selector：在模块之间做动态路由

模块池建立之后，系统还必须回答一个关键问题：

**在每一步、每个样本、每个训练阶段，应该更信任哪些模块？**

selector 的作用就是对这一问题做可学习的动态回答。

### 3.3.1 selector 的功能

selector 会根据当前训练状态或局部行为特征，对多个模块进行加权或路由，从而决定最终进入 learner 的辅助奖励由哪些模块主导。

因此，系统中的辅助奖励不是多个模块的简单平均，而是经过动态选择之后的结果。

### 3.3.2 selector 的重要性

如果没有 selector，模块再多也只是静态叠加，无法体现训练阶段差异；
有了 selector，系统才真正具备了"根据训练状态调整 shaping 结构"的能力。

### 3.3.3 当前重点监控的 selector 指标

当前框架特别关注以下几个统计量：

- `selector_entropy`
  - 衡量选择分布是否过于尖锐；
  - 过低通常意味着 selector 正在塌缩到少数模块。

- `selector_top1_switch_rate`
  - 衡量最高权重模块切换是否频繁；
  - 可用于观察路由是否过度震荡。

- `selector_balance`
  - 衡量模块使用是否长期失衡；
  - 该指标在后续的 update trigger 中具有重要作用。

## 3.4 learner 中的辅助奖励注入

这是模块化奖励系统与 RL 主体真正耦合的核心位置，位于 `src/learners/modular_reward_learner.py`。

### 3.4.1 原始思路

最直接的做法是将环境 reward 与辅助 reward 线性叠加：

```python
shaped_rewards = rewards + beta * auxiliary_reward
```

其中：

- `rewards` 为环境原始回报；
- `auxiliary_reward` 为模块池产生的团队级辅助信号；
- `beta` 用于控制 shaping 强度。

### 3.4.2 核心风险：reward hijack

如果 `beta * auxiliary_reward` 在局部时间段过大，就会出现一个明显风险：

- 模型表面上在优化；
- 但真正被优化的是 shaping 所暗示的局部目标；
- 而不是环境真正关心的长期任务目标。

这就是高 beta 情况下常见的 reward hijack 问题。

### 3.4.3 当前改进：对 shaping delta 做有界控制

当前框架没有改动环境原始 reward，而是只对附加项做约束：

```python
shaped_reward_delta = effective_beta * team_auxiliary_reward
clipped_shaped_reward_delta = clamp(shaped_reward_delta, -c, c)
shaped_rewards = rewards + clipped_shaped_reward_delta
```

其核心思想是：

- 原始环境 reward 保持不变；
- 只限制辅助奖励对 TD target 的瞬时冲击；
- 保留 shaping 的方向性，但避免其局部压过真实任务信号。

这一步本质上不是简单继续调 beta，而是在 shaping 注入路径上加了一层保险丝。beta 决定理论允许多大影响，而 clip 决定局部瞬时影响不能失控。

### 3.4.4 新增可观测量

为了验证该保护机制是否真实发挥作用，当前框架新增了：

- `shaped_reward_delta_mean`
- `shaped_reward_delta_clip_ratio`

它们分别用于回答：

- 当前平均注入了多少 shaping 增量；
- 有多少比例的 shaping 增量被截断。

这样在 beta 消融实验中，分析不再局限于 win rate，还可以直接观察高 beta 收益是否来自有效引导，还是来自过强注入。

## 3.5 模块生命周期机制：让模块可以在线迭代

这是当前框架最接近论文创新点的部分之一。

系统并不假设初始化出的模块池永远正确，而是允许模块经历以下生命周期：

1. 正常使用；
2. 被识别为低信号或低质量模块；
3. 触发候选替换；
4. 候选模块进入 shadow 验证；
5. 根据效果选择 promote 或 rollback。

### 3.5.1 为什么需要生命周期机制

一个模块可能：

- 在训练早期有效，但在中后期失效；
- 在某个训练阶段有帮助，但随后开始误导优化；
- 名义上看起来合理，但实际 contribution 很低；
- 长期被 selector 弃用，说明其结构价值已经下降。

如果没有生命周期机制，模块池会随着训练推进逐渐老化。当前框架的目标，就是让模块池本身也成为一个可以在线更新的对象。

### 3.5.2 低信号判据

系统当前主要基于以下指标识别弱模块：

- usage
- contribution
- activation

这些信号共同用于判断：

- 绝对低信号模块；
- 相对偏弱模块。

### 3.5.3 替换的安全链路

当前系统没有采用"一旦判定弱模块就立刻覆盖"的激进更新方式，而是使用了分阶段机制：

- `stage_candidate`
- `candidate shadow`
- `promote`
- `rollback`

其意义在于：

- 先挂接候选模块；
- 再观察关键指标是否改善；
- 改善后正式晋升；
- 若表现变差，则安全回滚。

因此，模块更新变成了一种低风险在线试验，而不是不可逆替换。

## 3.6 update trigger：何时认为该换模块

这个部分是当前框架近期重点增强的部分。

### 3.6.1 原始问题

早期的触发逻辑更接近"明显坏掉才更新"：

- 训练停滞；
- selector 塌缩；
- 模块信号极差。

只有在这些明显异常出现后，系统才会考虑替换。

但实际训练中存在一种更隐蔽的情况：

**训练表面仍然在上涨，但 selector 结构已经明显偏科，说明系统正在朝某种狭窄、次优但未立刻崩溃的方向固化。**

这类情况如果不提前干预，后期往往更容易出现性能问题。

### 3.6.2 新增的两个关键概念

#### 1）improving
用于判断训练是否仍处于提升状态，主要依赖：

- `latest_test_return`
- `latest_test_win_rate`

#### 2）structural_bias
用于判断 selector 是否已经出现结构性失衡，主要依赖：

- `selector_entropy`
- `selector_top1_switch_rate`
- `selector_balance`
- 模块 usage gap 等历史信号

于是系统就能识别一种更复杂的状态：

- 训练还在上涨；
- 但模块使用结构已经严重偏斜；
- 说明现有模块结构可能正在把系统推向狭窄策略。

### 3.6.3 新增触发模式

当前框架将这种情形抽象为新的触发模式：

- `relative_low_signal_improving`

它的含义是：

> 即使训练没有停滞，只要已经出现明显结构性偏科，也可以对相对弱模块发起替换尝试。

这比原来的"等坏掉再修"更主动，更符合在线模块迭代框架的整体目标。

## 3.7 LLM 模块生成与正交性约束

当系统决定替换模块后，下一步就是生成候选模块。这里虽然使用了 LLM，但并不是无约束自由生成。

### 3.7.1 LLM 的输出对象

LLM 输出的是 reward module proposal，即新的奖励逻辑描述或可执行草案，用于替换当前池中的弱模块。

### 3.7.2 两层验证机制

当前生成链路至少包含两层验证：

1. **静态验证**
   - 结构是否可解析；
   - 基本格式与约束是否满足。

2. **dry-run 验证**
   - 候选模块能否在现有输入上正常运行；
   - 是否会破坏接口或输出形式。

因此，并不是所有生成结果都会进入实际训练。

### 3.7.3 轻量正交性门

一个常见问题是：

- LLM 表面上生成了新模块；
- 但本质仍是旧模块的同家族弱变体；
- 最终导致模块池越替换越同质化。

为此，当前框架增加了 family / coverage 层面的轻量正交性约束：

- 若 candidate 与 target 属于同一家族，且该 family 在池中已不稀缺，则拒绝；
- prompt 中加入 family soft cap，鼓励转向其他行为家族；
- 对明显冗余的 proposal 进行过滤。

其目标不是构造昂贵的复杂多样性指标，而是用较低成本避免最常见的冗余替换。

## 3.8 当前实验设计与验证目标

当前实验并不只是想回答"这个框架是否有效"，而是在进一步回答：

1. 固定 beta 与递增 beta 哪种更适合当前 modular reward 框架；
2. 在固定 beta 条件下，最合适的 shaping 强度落在哪个区间；
3. 模块迭代是否真正发生，以及在什么条件下发生；
4. 高 beta 的收益是否来自有效指导，还是来自辅助奖励对主目标的侵入。

### 3.8.1 当前一个关键观察

目前已经观察到：

**固定 beta 带来的性能提升明显强于递增 beta。**

这表明，在当前 modular reward 框架下，过于保守的 ramp 可能削弱了 reward agent 在关键训练早期的指导强度。

### 3.8.2 当前实验目标

因此，当前新的实验目标是：

**在固定 beta 条件下，从 0.20 到 0.40 的区间中找到最合适的 shaping 强度。**

其背后的平衡逻辑是：

- beta 太低：指导不足，模块价值无法充分发挥；
- beta 太高：辅助奖励开始侵入主目标，训练后期可能不稳；
- beta 适中：既能提供足够先验，又不会劫持 QMIX 的主优化方向。

### 3.8.3 实验中真正需要比较的指标

当前这批实验最终需要同时观察四类结果：

1. **任务结果**
   - `test_return_mean`
   - `test_battle_won_mean`

2. **奖励注入强度**
   - `shaped_reward_delta_mean`
   - `shaped_reward_delta_clip_ratio`

3. **selector 结构状态**
   - entropy
   - balance
   - switch rate

4. **模块生命周期事件**
   - 是否出现 `stage_candidate`
   - 是否出现 `promote`
   - 是否出现 `rollback`
   - 哪些模块反复成为替换目标

因此，实验最终关注的不是单纯"哪个 beta 分数更高"，而是：

**哪个 beta 能够在任务收益、奖励稳定性和模块迭代质量之间取得最好平衡。**

如果用更接近论文摘要的话来概括，当前框架可以表述为：

> 该方法在 QMIX 主体上引入一个由 LLM 初始化并可在线更新的模块化奖励代理，通过动态模块选择、受控辅助奖励注入以及安全的模块生命周期管理，在不修改环境与主策略学习框架的前提下，实现对多智能体协作行为的可解释、可迭代奖励塑形。

> 当前工作不是在训练一个直接决策的 LLM-RL 系统，而是在训练一个能够自我修正奖励结构的多智能体学习系统。

# 五、当前框架的核心贡献

如果用论文式贡献点归纳，可以将当前工作总结为以下三条：

### 贡献 1
提出一种面向多智能体任务的模块化奖励代理，将复杂协作先验拆解为可选择、可监控、可替换的 reward modules。

### 贡献 2
提出一套在线模块生命周期机制，通过 `stage_candidate -> promote / rollback` 的安全链路，使奖励模块能够在训练过程中真实迭代，而不是静态固定。

### 贡献 3
提出受控辅助奖励注入与结构偏科触发机制，在保留 shaping 指导能力的同时，降低高强度辅助奖励劫持训练目标的风险，并使更新能够在"仍在提升但结构失衡"时提前发生。
